# DevCycle 002: Build a New Automatic Butter Churner from the BUILD Menu

**Status:** Closed — does not yet work end-to-end. 19 phases of fixes landed (build, visibility, the interaction menu, milk tracking, container recovery), but the cycle is being closed with known remaining problems rather than continuing further; see Completion Summary. Continues in DevCycle 3.
**Start Date:** 2026-08-31
**Target Completion:** Closed 2026-08-31 (incomplete — see Completion Summary)
**Focus:** Drop DevCycle 1's washing-machine-conversion approach entirely. `AutoButterChurn` is now a brand-new object the player builds directly from the BUILD menu, requiring one Screwdriver (kept) and one Plank (consumed), and it simply appears on the square once built. Everything after that — the fill/production mechanic — is unchanged from what DC1 Phase 17 was reaching for: the `Resources` + `DryingCraftLogic` pattern investigated in `doc/ideas/claude_dryingRackSimilarity.md`, with a fixed 20 L / 5-minute / 4-stick production cycle.

---

## Goal

DC1 spent almost its entire cycle (Phases 1, 6–17) fighting the washing-machine-to-`AutoButterChurn` conversion flow — module-qualified entity names, sprite-row collisions, a registered-but-blank placeholder sprite, and finally a `component FluidContainer` redesign that was implemented but confirmed not working, with no captured diagnostic detail on why. That entire mechanism is now out of scope. This cycle replaces it with the ordinary, well-trodden path every other player-built fixture in the game uses: a BUILD-menu construction recipe. No washing machine, no conversion timed action, no context-menu gate on an existing world object — the player picks "Automatic Butter Churner" from the BUILD menu like they would a `Drying_Rack` or any other placeable fixture, supplies a screwdriver (kept, not consumed) and a plank (consumed), and the entity appears.

Once it exists, its behavior is exactly what DC1 Phase 17 was trying to reach before the conversion mechanics ate the whole cycle: a drying-rack-style fill/production loop built on `component Resources` + `component DryingCraftLogic`, not the trough/pour-style `FluidContainer` interaction DC1 Phase 17 chased and failed to get working alongside automatic batching.

This cycle also keeps DC1's already-decided production numbers: **the entire conversion of a full 20 L tank into 4 sticks of butter should take 5 minutes of game time.**

## Desired Outcome

The mod loads in Project Zomboid B42 with no script parse errors. A player can:

1. Open the BUILD menu, find "Automatic Butter Churner" as a buildable option, and place it — requiring one Screwdriver in inventory (kept, not consumed, same `mode:keep` tool pattern used elsewhere in this project) and one Plank (consumed) — with no washing machine, no existing world object, and no context-menu gate involved. The entity just appears where placed.
2. **(Superseded by Phase 8 — see below.)** ~~Interact with the placed `AutoButterChurn` entity and get the same kind of crafting-style window a `Drying_Rack` opens (`ISEntityWindow`).~~ The entity has no crafting window at all (`uiEnabled = false`) — right-clicking it while holding a milk container offers the ordinary vanilla "pour fluid in" option instead, the same interaction rain barrels and troughs use.
3. **(Superseded by Phase 8 — see below.)** ~~Drag a milk-holding item onto the entity's input slot.~~ Pour milk in from a held container (up to 20 L, Cow/Sheep Milk only) via that vanilla pour option — the container itself stays in the player's inventory, only the fluid transfers. (Phase 6 had first revised this to "drag the whole container into an item slot"; Phase 8 revised it again, since that still required physically placing the container, which wasn't the actual want.)
4. Once poured in, it starts consuming milk in 5 L increments automatically, with no Start button and no further player interaction, producing 1 Butter per increment until the tank runs dry — driven by a hand-rolled Lua tick (`AutoButterChurnCode.lua`, `Events.EveryTenMinutes`) rather than `StartMode = Automatic`/`DryingCraftLogic`, since `CraftLogic`-family components can't read a plain `FluidContainer` at all (Phase 8).
5. Confirm the timing: **a full 20 L fill (4 batches of 5 L → 1 Butter each) completes in 5 minutes of game time** — i.e. 75 seconds per 5 L batch (300 seconds ÷ 4 batches), checked via the tick's own elapsed-in-game-time math (`GameTime.getInstance():getWorldAgeHours()`), not `DryingCraftLogic`'s temperature/wetness pacing — that pacing model no longer applies at all now that `DryingCraftLogic` isn't used (a simplification from the original target, which accepted colder/rained-on slowdown as a deliberate tradeoff; the hand-rolled tick has no such model unless one is added later).

**Revised by Phase 6:** the "20 L tank" is no longer an abstract fluid gauge tracked by the entity itself — it's realized by whatever milk container the player drags in. A full `BucketLargeWood` (20 L) reproduces the original 4-batch/5-minute numbers exactly; a smaller container (e.g. a 1 L `MilkBottle`) just yields fewer batches before it needs replacing. See Phase 6 for why, and Phase 2/3 for the resulting script shape.

### Phase 5: First-Load Bugfixes

**Status:** Work Complete — fixes applied, re-test pending

The first real in-game load attempt (2026-08-31) failed at world load, before a save could open:

```
ERROR: General      f:0> GameLoadingState$1.run> Exception thrown
    zombie.world.WorldDictionaryException: World loading could not proceed, there are script load errors.
        zombie.iso.IsoWorld.init(IsoWorld.java:2789)
```

The full `WorldDictionaryException` only says the real error is earlier in the log — `console.txt`/the debug log for the run (`Logs/logs_2026-08-31/2026-08-31_10-02_DebugLog.txt`, the file at `Zomboid/Logs/` matching the run's timestamp) showed two distinct problems, both in this mod's own scripts:

- [x] **Bug 1 — `XuiSkin 'Pseudonymous.default' ignored, skin needs to be module Base.`** (`XuiManager.ParseScripts`), immediately followed by `Cannot find entity ui info: ES_AutoButterChurn, attempting default....` (`XuiSkin.getEntityUiStyle`, logged twice). **Root cause:** `entity_AutoButterChurn_xuiSkin.txt` declared `module Pseudonymous`, but every vanilla `xuiSkin` block — including both reference files this mod was modeled on, `entity_butter_churn_xuiSkin.txt` and `entity_Drying_Rack_xuiSkin.txt` — is `module Base`. `xuiSkin` blocks are apparently required to live in `module Base` regardless of which module the entity itself belongs to (unlike entity/fluidFilter script lookups, which use the declaring mod's own module and just need to be referenced module-qualified — the opposite kind of gotcha from DC1 Phase 14's lesson, easy to over-apply in the wrong direction). Because the whole xuiSkin block was silently discarded, `ES_AutoButterChurn` had no UI info at all: no `DisplayName`, no `Icon`, and critically no `LuaWindowClass = ISEntityWindow` — this alone would have reintroduced Phase 2's exact target bug (wrong/default crafting window) even if nothing else had gone wrong. Not fatal by itself (a WARN, not an ERROR), but a real functional bug. **Fix:** changed `entity_AutoButterChurn_xuiSkin.txt`'s `module Pseudonymous` to `module Base`.
- [x] **Bug 2 (fatal) — `Sprite 'crafted_05_72' is duplicate. entity script: AutoButterChurn`** (`SpriteConfigManager.parseEntityScript`), which escalated into the `WorldDictionaryException` above. **Root cause:** `crafted_05_72` is vanilla's own `ChurnBucket` entity's declared `SpriteConfig` row (`entity_butter_churn.txt`) — this is the identical collision DC1 Phase 7 hit and fixed once already, reintroduced here by mistake. The reason it came back: DC1 Phase 16 established that `crafted_05_72` is safe to reuse only as the *runtime* `sprite` argument to `square:addWorkstationEntity(...)`, because that call path sets `IsoThumpable.closedSprite` directly via `IsoSpriteManager` with no uniqueness check — a completely different, uncollide-checked code path from a *declared* `component SpriteConfig` row, which `SpriteConfigManager` does check for duplicates at load time (the same check Phase 7 originally hit). DC2 no longer calls `addWorkstationEntity` at all — Phase 1 replaced that whole mechanism with a `component CraftRecipe` BUILD-menu placement, which places the entity via its own declared `SpriteConfig` — so the "safe as a runtime argument" fact carried over from DC1 no longer applied, and `crafted_05_72` collided exactly the way Phase 7 already demonstrated it would. **Fix:** changed the declared row (in both `component SpriteConfig` and all three `component SpriteOverlayConfig` progress tiers, which were also set to the same placeholder) from `crafted_05_72` to `crafted_05_160` — a `crafted_05_*` index confirmed, by grepping every entity script in `media/scripts` for `crafted_05_\d+`, to not be declared by any other entity (`leather_prep`, `ChurnBucket`, and the `welding_*`/`carpentry_*` furniture entities between them claim 4–147 in scattered clusters; `160` sits well outside all of it, in the unexplored 148–200 range DC1's Phase 12 diagnostic confirmed is fully *registered* in `IsoSpriteManager` but never checked for *drawn* content).
- [x] Re-copied the mod to the local Zomboid mods folder via `utilities\CopyModToZomboid.bat PseudoButterChurner` after both fixes.
- [ ] **Re-launch B42 and confirm the mod now loads past world init with no script-load errors.** Not yet re-tested.
- [ ] **If `crafted_05_160` is also invisible or renders garbled:** this would be the third `crafted_05_*` guess to fail (after DC1's `crafted_05_60` and `crafted_05_78`, both registered-but-blank). At that point, stop guessing on the shared sheet entirely and do minimal real custom art instead (a small mod-owned texture pack + tile definition, the pattern `PseudoSaltWell42_19` already uses) — this was already DC1's own conclusion after its second failed guess, and a third failure would confirm it rather than just suggest it.

**Technical Notes:**
Bug 1's direction is the mirror image of DC1 Phase 14's lesson: Phase 14 learned that *entity* names need their module prefix when referenced bare (`Pseudonymous.AutoButterChurn`, not `AutoButterChurn`). This bug is the opposite shape — a whole *xuiSkin* block needs to declare `module Base` regardless of the entity's actual module, not be self-qualified the way entity/fluidFilter references are. Worth remembering as a distinct rule, not a generalization of Phase 14's: different script types in this engine have different module-scoping rules, and each one needs its own confirmation rather than assuming they all behave alike.

Bug 2 is a direct consequence of Phase 1's own architecture change (BUILD-menu `CraftRecipe` placement instead of `addWorkstationEntity`) invalidating a fact from DC1 that was true only in DC1's specific mechanism. This is exactly the kind of thing this project's process is meant to catch via in-game verification rather than static reasoning — see `feedback_dont_remove_diagnostics_before_confirmed_fix` and DC1's own repeated lesson that decompiled-source-level confidence isn't the same as confirmed-working.

- [x] **Bug 4 — the entity's `ISEntityWindow` shows no available milk, even with a full milk container in inventory. Root cause traced and confirmed in the client Lua UI code, not a data/script problem:**
  - `ISWidgetCraftLogicInputControl:createDynamicChildren()` (`media/lua/client/Entity/ISUI/Components/Crafting/ISWidgetCraftLogicInputControl.lua:16`) — the panel that actually builds the drag-and-drop input slots inside the recipe view of `ISEntityWindow`/`ISCraftLogicPanel` — queries the entity's `Resources` component with `getResourcesFromGroup(self.inputsGroupName, ArrayList.new(), ResourceIO.Input, ResourceType.Item)`, **hardcoded to `ResourceType.Item`**. Phase 2's whole design (a `Fluid@Input@20` resource, filled by dragging a milk-holding item onto the entity window) is built on a UI path that doesn't exist for any shipped or custom entity — the design doc's own caveat ("not exercised by any shipped entity") undersold the risk; this isn't just "untested," it's currently unreachable through the standard window.

### Phase 8: Bug 6, Corrected Again — the Milk Should Drain Out, the Container Should Stay With the Player

**Status:** Work Complete — decision made (option 2), implemented, copied to the live mod folder; re-test pending

Bug 6 needed a second correction. Not "a button to remove the milk container from the slot" (Phase 7's first guess), not "a button to pull the milk container into the slot" (Phase 7's second guess, based on the `showSelectInputsButton` mechanism) — the actual want is: **the player keeps holding the bucket; only the milk itself should transfer into the machine**, the same way filling a rain barrel or trough works — pour the fluid in, walk away with the (now emptier) container.

This is, precisely, the interaction DC1 Phase 17 already built and called "the trough-style pour UX" — and the reason Phase 2 of *this* cycle deliberately didn't use it (see `doc/ideas/claude_dryingRackSimilarity.md` and this document's own Notes and Risks below). Restating why, now that it's the actual requirement again rather than a hypothetical:

- Project Zomboid's simple "pour a held container's contents in" interaction (the one troughs, rain barrels, and the Amphora get for free) is gated on one thing: the target having a plain `component FluidContainer`. It has nothing to do with entities vs. legacy objects, `CraftLogic` vs. anything else — `ISWorldObjectContextMenuLogic.fetch()` just checks `hasComponent(ComponentType.FluidContainer)` and offers the pour submenu automatically.
- `DryingCraftLogic`/`CraftLogic` (the component driving this entity's automatic batching) can only ever read its inputs from a named `component Resources` group — never from a sibling `component FluidContainer`. This was re-confirmed, not assumed, across DC1 Phase 17 and this cycle's Phase 6/Phase 2.
- Phase 6 additionally confirmed the standard entity crafting window (`ISEntityWindow`/`ISCraftLogicPanel`/`ISWidgetCraftLogicInputControl`) never renders a `Fluid@Input` `Resources` entry either — `ISFluidSlotPanel`/`ISFluidSlot` (the widgets that *do* have their own "Transfer Fluids" button, opening `ISFluidTransferUI` — exactly a "drain from a held container, don't place it" interaction) exist and are fully working, but `ISCraftLogicPanel:createChildren()` never instantiates them; `createFluidSlotPanel()` is dead code from this window's perspective.

Put together: **every currently-known way to get automatic `DryingCraftLogic`/`CraftLogic` batching in this engine version requires the input to live in an `Item@Input` `Resources` slot — which means placing a physical item, not draining one in place.** There is no confirmed path in this codebase, across two DevCycles now, that gives both "batches automatically with no player babysitting" and "the container never leaves the player's hands." This is the same structural tension DC1's Phase 17 hit, from a different angle.

**Real options, none of them free:**

1. **Wire up the entity window's own fluid UI ourselves.** `ISFluidSlotPanel`/`ISFluidSlot` already exist and already have the right "Transfer Fluids" button/behavior — they're just never instantiated for a `CraftLogic`-family entity window. This would mean new client Lua (a custom `ISCraftLogicPanel`-alike, or overriding `createChildren`) to actually call the existing-but-unused `createFluidSlotPanel()` and wire a `Fluid@Input` `Resources` group (Phase 2's original design, reverted in Phase 6) into it. No shipped or prior-attempted precedent for this specific combination exists anywhere in this project's history — genuinely new UI code, real implementation risk, but it's the only option that keeps both "automatic" and "don't place the container."
2. **Go back to the trough/pour UX and give up `DryingCraftLogic`-driven automatic batching**, reviving something close to DC1 Phase 17's design: `component FluidContainer` (free pour-in UI, no custom Lua needed for filling) plus a hand-rolled Lua tick system for the actual milk→butter production (DC1's `ModData`-backed registry + `Events.EveryTenMinutes`, or the more robust `SGlobalObjectSystem` framework DC1's own Phase 17 notes flagged as a better fit but didn't adopt). DC1 built exactly this once already and it was reported "did not work," but *why* was never diagnosed before DC1 closed — this cycle now has much more UI/engine understanding banked (the xuiSkin module rule, the sprite-declaration-vs-runtime-override distinction, the `Resources`/`CraftLogic` fluid gap) that DC1 didn't have while debugging it the first time, so a second attempt wouldn't be starting from the same blind spot.
3. **Keep the current `Item@Input` design (container must be placed) and accept that's the interaction**, same tradeoff Phase 6/7 already made — explicitly rejected by this message, listed only for completeness.

The greater-than-only acceptance rule is a simple, targeted fix rather than trying to distinguish fill-events from drain-events by inspecting *why* the callback fired (which isn't exposed to the handler at all) — worth keeping in mind if a future edit needs to also handle a player legitimately reducing the amount (e.g. manually withdrawing milk), which this rule would currently also ignore.

### Phase 18: The Container Itself Was Never Addressed — Fixed, With a Bigger Implication for Multi-Batch Runs

**Status:** Work Complete — implemented, copied to the live mod folder; re-test pending

Direct question from the user after Phase 17: had the container-disappearing half of the original bug report actually been fixed? It hadn't — every fix from Phase 14 through 17 was about the *milk quantity* tracking; nothing had gone back to check whether the bucket item itself survives a batch.

- [x] **Traced the removal precisely.** `entity_AutoButterChurn.txt`'s `item 1 [*]` recipe line had no `mode:keep`. In `CraftRecipeManager.consumeInputItem(InputScript, List<Resource>, ...)` (`zombie42_20_4/entity/components/crafting/recipe/CraftRecipeManager.java:673-689`), the item gets removed from `churn_inputs` via `resourceItem.removeItem(item)` whenever `!input.isKeep() || canMoveItemsToOutput` is true. First attempt: added `mode:keep` to the recipe line, on the reasonable assumption that mirrors how every tool/kept-item in this project's other recipes works.
- [x] **That assumption didn't survive contact with the rest of the condition.** `canMoveItemsToOutput` traces back to `Resource.canMoveItemsToOutput()` (`zombie42_20_4/entity/components/resources/Resource.java:301-303`) — the base-class implementation is `return true;` unconditionally, and `ResourceItem` (the class actually backing our `Item@Input` slot) doesn't override it. Since the removal condition is an **OR**, and one side of it is hard-coded `true`, `mode:keep` cannot ever prevent the removal on its own — the whole condition is always true regardless. Caught this by re-reading the exact code before claiming the `mode:keep` fix worked, rather than asserting it without checking (kept `mode:keep` in the recipe anyway — harmless, and may matter for other engine paths not examined here).
- [x] **Bigger implication found while fixing this: the container is removed after *every* completed batch, not just the last one.** This means Phase 14's auto-continue call (`craftLogic:start(player)` for a second, third, fourth batch) would find an *empty* input slot and silently fail to start — a second root cause for "only ever get 1 stick of butter," independent of the milk-tracking fixes in Phases 15-17.
- [x] **Fix:** rewrote `onBatchComplete` to check `resource:peekItem()` after every batch, not just the last. If the container is gone (now the confirmed common case), it's recreated via `instanceItem(itemType)` (the type captured by the existing milk-tracking snapshot) with its `FluidContainer` set to the correct locally-tracked leftover amount. If the run is continuing, the rebuilt container is put back into `churn_inputs` via `resource:offerItems({newItem})` *before* `craftLogic:start(player)` is re-issued, so the next batch has something to consume. If the run has finished, the rebuilt container goes directly into the using player's inventory instead (`player:getInventory():AddItem(newItem)`) — matching "the bucket should come back to me," not just "the bucket should still exist somewhere."
- [x] Re-copied the mod to the local Zomboid mods folder via `utilities\CopyModToZomboid.bat PseudoButterChurner`.
- [ ] **Confirm in-game**: a 10 L bucket should produce 2 Butter and end up back in the player's inventory holding 0 L; a 20 L bucket should produce 4 and likewise return empty; watch for `container was removed, rebuilt into churn_inputs for the next batch` on intermediate batches and `container was removed, recreated in <player>'s inventory` on the final one. Not yet re-tested — and this is the first real test of whether multi-batch auto-continuation ever actually worked, since the container being missing may have silently defeated it every time before now.

**Technical Notes:**
This phase is a direct answer to a direct question ("did you fix X?") that the honest answer to was no — worth noting because the fix for it also turned out to explain a second, previously-unexplained symptom (multi-batch auto-continue's apparent total failure) that had been sitting underneath the milk-accounting bugs the whole time. `instanceItem(fullType)` and `player:getInventory():AddItem(item)` are the same primitives used elsewhere in vanilla for recreating/handing over items (e.g. `ISBuildIsoEntity.lua`'s own use of `instanceItem`); `resource:offerItems(ArrayList)` is the same call `ISItemSlot:itemDropped()` uses for a player's own manual drag-and-drop, reused here for a programmatic equivalent.

### Phase 19: The Rebuilt Container's Milk Was Never Actually Set — `adjustAmount` Doesn't Work on an Empty Container

**Status:** Work Complete — implemented, copied to the live mod folder; re-test pending

Phase 18's fix got the container itself back correctly, but a 10 L bucket still only produced 1 stick, not 2. The user's log made the second failure precise: `container was removed, rebuilt into churn_inputs with 5 L for the next batch` was immediately followed by `AutoButterChurnCode: item slot contents changed, re-snapshotting` reporting the rebuilt container held **0 L**, not the 5 L just set — and no second `batch complete` ever fired for either test run in the log, meaning the second craft never actually started.

- [x] **Root cause: `FluidContainer:adjustAmount(newAmount)` is a no-op whenever the container is already empty** (`zombie42_20_4/entity/components/fluids/FluidContainer.java:706-708` — the whole method body is wrapped in `if (!this.isEmpty()) { ... }`). Every container `AutoButterChurnCode.lua` was calling `adjustAmount` on — both the freshly `instanceItem`'d replacement from Phase 18, and even the "still in slot" original from Phase 15 onward — is confirmed empty at that point (Phase 15 already established the engine always drains fully). `adjustAmount` only *rescales* fluid that's already present; it cannot put fluid into a container that has none. Every "restored X L leftover" log line since Phase 15 was true only of this mod's own tracked bookkeeping — the actual `FluidContainer` was silently never being touched.
- [x] **Fix:** replaced every `fc:adjustAmount(amount)` call with `fc:addFluid("CowMilk", amount)` (`FluidContainer.addFluid(String fluidType, float amount)`, confirmed at `FluidContainer.java:927-929` to work regardless of whether the container starts empty). Milk type isn't tracked separately from the original container (the recipe's own `mode:mixture` already treats Cow/Sheep Milk as interchangeable), so `CowMilk` is used as a reasonable default for any leftover, whether restoring the original container or a rebuilt replacement.
- [x] Re-copied the mod to the local Zomboid mods folder via `utilities\CopyModToZomboid.bat PseudoButterChurner`.
- [ ] **Confirm in-game**: a 10 L bucket should now produce 2 Butter, with the log showing the rebuilt container actually holding 5 L (not 0) after the first batch, and a second `batch complete` line should finally appear. Not yet re-tested.

**Technical Notes:**
This is the third distinct bug found underneath what looked, from the outside, like a single "quantity isn't right" report (Phases 15/17's snapshot-timing bugs, Phase 18's missing container, now this) — each one only became visible once the previous one was fixed and testing could get one step further into the actual flow. Worth remembering for any future fluid-container manipulation in this mod: `adjustAmount` and `addFluid` are not interchangeable — `adjustAmount` rescales an existing amount, `addFluid` is required to put fluid into an empty container at all.

**Lessons / Notes for DevCycle 3:**
- This cycle's single biggest recurring failure mode: **static reading of decompiled Java repeatedly failed to predict actual runtime behavior** for the specific combination of `component Resources` + `DryingCraftLogic` + a `-fluid`-modified `Item@Input` slot — not once (expected, given this project's whole history) but *many* times in a row (Phases 14, 15, 18, 19 each individually corrected a wrong prediction from the phase before).
