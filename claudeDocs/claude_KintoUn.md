# Kinto-un (Flying Nimbus) Mod Analysis

**Created:** 2026-11-12
**Subject:** `notmymods/KintoUn/` (mod id `KintoUn`, author elp4nsho, modversion 1.0.0, `versionMin=42.15.0`)
**Game build checked against:** v42.20.4 (`zombie42_20_4/` Java, `media42_20_4/` Lua)
**Goal:** Understand how the mod makes the player fly, and decide whether a simple single-player levitation mod (travel at running speed, plus levitate up and down) can be built from the same approach.

> Note on the path: the request named `notmymods/KintoUn.42`. The folder is `notmymods/KintoUn/`, and its game content is in the `42/` subfolder (`notmymods/KintoUn/42/`). All paths below are relative to `notmymods/KintoUn/42/`.

---

## 1. Summary

- Kinto-un is **almost entirely client-side Lua** plus one wearable item. All the flying is in one 181-line file, `media/lua/client/KintoUn_Client.lua`.
- It does **not** use any special engine flight feature. It moves the player by writing the player's X, Y and Z every tick (`setX`, `setY`, `setZ`, `setLastZ`), the same trick vanilla uses in its fast-move debug cheat (`media42_20_4/lua/client/DebugUIs/ISFastTeleportMove.lua`).
- A custom animation set replaces walk, run, sprint, idle and fall with a standing "floating" pose while the cloud is worn.
- **A single-player levitation mod is clearly feasible** with the same technique, and most of the work can be much simpler than this mod (no cloud model, no custom animation required).
- **One real compatibility problem for v42.20.4:** the mod reads movement keys with `KeybindId.FORWARD` and similar, but `KeybindId` exists nowhere in the v42.20.4 Java or Lua (or in the 42.19 and 42.11.0 Java). On this build the in-air horizontal movement code would error (it is caught by `pcall` and printed). See section 5.1. This must be confirmed in game before copying that code.

## 3. How the Flight Works (`KintoUn_Client.lua`)

### 3.1 State and trigger

- `KintoUn.isRiding(player)` is true when the player is wearing `KintoUn.KintoUn` (a wear slot scan, `KintoUn_Shared.lua:5`).
- Every `OnPlayerUpdate` (`KintoUn_Client.lua:166`, only for the local player) it sets the animation variable `player:setVariable("KintoUnRide", on)` (line 136). The AnimSet XMLs use that variable as a condition, so the floating pose replaces vanilla walk, run, sprint, idle, and fall animations (priority 20, condition priority 50).
- Everything is wrapped in `pcall`, so an error prints `[KintoUn] error: ...` and the mod carries on.

### 3.2 Horizontal movement on the ground (lines 157 to 163)

The game itself still decides the player is walking or running. The mod only adds extra distance on top of it:

1. If the player is not moving, do nothing.
2. Speed is the sandbox `Speed` (default 7 tiles per second), times 1.8 if sprinting, times 1.4 if running.
3. `push(player, speed * dt)` moves the player along the forward direction.

So on the ground the mod is a speed boost that adds to vanilla movement; it is not a replacement.

### 3.3 Horizontal movement in the air (lines 141 to 155)

The code's own comment explains that while airborne the game puts the player in the falling state and will not walk them. So in the air the mod reads the movement keys directly (`keyDir`, lines 89 to 99) and converts them to isometric directions (forward = -1,-1; back = +1,+1; left = -1,+1; right = +1,-1), sets the player's forward direction, and calls `push`.

- It speeds up with height: `speed * (1 + 0.25 * floorsAboveGround)`, so 8 floors up is about 3 times faster (`HEIGHT_BOOST`).
- Run and sprint keys multiply by 1.4 and 1.8.
- Aiming (`player:isAiming()`) turns the mod's movement off (line 139).

### 3.4 `push`: stepped movement with collision (lines 57 to 79)

- Moves in steps of 0.2 tiles (`STEP`) so fast movement cannot skip over a wall.
- Before each step it computes the squares it is leaving and entering at the player's current floor level and calls `blocked(from, to, high)` (lines 45 to 55):
  - A solid destination always blocks.
  - If the player is more than 0.3 floors above the ground (`LOW`), it can pass over fences, furniture and cars: only walls, windows and doors block (`isWallTo`, `isWindowTo`, `isDoorTo`).
  - Near the ground, normal blocking applies (`isBlockedTo` or `not to:isFree(false)`).
  - A missing square in the air counts as free air; on the ground a missing square blocks.
- Then it writes `player:setX(nx)` and `player:setY(ny)`.

### 3.5 Altitude (lines 102 to 127, plus `holdZ` at 81 to 85 and the tick hook at 172 to 177)

- `alt[player]` stores the held height. `nil` means "on the ground, let the game decide."
- Holding the up key (default `.`) climbs at 1.2 floors per second, capped at the sandbox `MaxHeight` (default 8). It will not pass through a solid floor above (checks `TreatAsSolidFloor()` on the square one level up).
- Holding the down key (default `,`) descends at 1.2 floors per second. Taking the cloud off in the air makes the player glide down at 0.6 floors per second.
- It lands when the held height reaches the first solid floor below (`groundAt`, which checks `TreatAsSolidFloor()` from the current floor down to 1, and treats level 0 as always solid). On landing it clears `alt` so the game takes over again.
- `holdZ` calls `setZ(z)`, `setLastZ(z)` and `setFallTime(0)`. It runs on both `OnPlayerUpdate` and `OnTick`. The `setFallTime(0)` is there so the landing does not count as a long fall. The `setZ` plus `setLastZ` pair is the same combination vanilla's `ISFastTeleportMove.moveZ` and its `OnTick` use (`ISFastTeleportMove.lua`, lines 15 to 21 and 69 to 77), which stops the engine from treating the height change as a fall.
- Keys for up and down are registered through `PZAPI.ModOptions` (key binds `UpKey` and `DownKey`), and read with `isKeyDown`.

### 3.5.1 Equipment slot and visuals

The item uses `BodyLocation = base:tail`, which exists in vanilla (`media42_20_4/lua/shared/NPCs/BodyLocations.lua:111`, `ItemBodyLocation.TAIL`), so it needs no custom body location. The worn cloud is a static model attached to bone `Bip01`.

## 5. Problems and Risks

### 5.1 `KeybindId` does not exist in the build I have (compatibility)

`keyDir` and the sprint and run checks call `getCore():getKey(KeybindId.FORWARD)`, `.BACKWARD`, `.LEFT`, `.RIGHT`, `.SPRINT` and `.RUN` (`KintoUn_Client.lua:92 to 95, 149, 151`).

- In v42.20.4, `Core.getKey` takes a **string** (`Core.java:2855`: `getKey(String keyName)`), and vanilla Lua calls it with strings such as `"Rotate building"`, and `getCore():isKey("Forward", key)` (`CFarming_Interact.lua:279`).
- `KeybindId` appears in none of: `media42_20_4/`, `media/`, `zombie42_20_4/`, `zombie42_19/`, `zombie42_11/`.
- So on this build, `KeybindId` is nil, indexing it fails, and `pcall` swallows the error and prints it every tick. That means **in-air horizontal movement (and in-air run and sprint multipliers) would not work**, although climbing and descending would, because those use the `ModOptions` keys. The mod declares `versionMin=42.15.0`, so it may target a different or newer build than the ones in this repo, which is why this needs to be confirmed in game rather than assumed.
- For our own mod we should use the string key names (`"Forward"`, `"Backward"`, `"Left"`, `"Right"`; I did not confirm the exact names for run and sprint and would look them up in `Core.java` or the game's key binding list before using them).

### 5.2 Multiplayer behavior

The mod moves the player by writing coordinates on the client. In multiplayer the server validates movement:

- `AntiCheatSpeed` (`network/anticheats/AntiCheatSpeed.java`) rejects a player whose reported speed exceeds a hard limit of 20, unless the player's role has teleport or fast-move capability. The mod's speed can exceed that: default 7, times 1.8 sprint, times up to 3 from height gives about 38. Whether `getSpeed()` is in the same unit as the mod's tiles per second I did not verify.
- `AntiCheatNoClip` checks for movement through walls and teleports a player back unless they have the no-clip or fast-move cheat. The mod's `blocked()` avoids walls, but flying over fences and furniture, and holding Z with no floor, may still look suspicious to the server. I did not trace the rest of its checks.
- Server option `AntiCheatSpeed` and `AntiCheatNoClip` levels default to 2 and 4 in `ServerOptions.java` (lines 200 and 201), so these could trigger on a default server.

None of this matters for a single-player mod. I did not test any of it in game.

### 5.3 Other observations

- **Known problem (reported by the user, 2026-11-12):** flying with Kinto-un shows a falling animation after a while, and the character can fall and die when close to the ground. Likely cause, from reading `IsoGameCharacter.updateFalling()` (`IsoGameCharacter.java:10105-10141`): the engine keeps adding to `lastFallSpeed` while the character is above the floor, and the mod resets only `fallTime`, which the landing damage does not read. Once `lastFallSpeed` is past the falling threshold the falling animation plays, and a large `lastFallSpeed` makes the engine's next step go below the floor and call `DoLand` with a big impact speed. The likely fix is also resetting `lastFallSpeed` (`setLastFallSpeed(0)`) and the falling flag every tick. See PseudoMagic DevCycle 006, Phase 5. Not yet confirmed in game.
- Original claim (partly wrong, see above): landing uses `setFallTime(0)` and sets `z` to the ground directly, so there is no fall damage. Pulling the cloud off at height gives a gentle glide, not a fall.
- A ceiling check only looks at the one square above (`TreatAsSolidFloor()` one floor up), so a tilted or odd roof could be passed.
- `groundAt` scans floors from the current height down to 1 and returns 0 if none is solid, so it never finds a floor below ground level (basements).
- The mod ignores vehicles (`not player:getVehicle()`), which is correct.
- Uses real-time `dt` (`getRealworldSecondsSinceLastUpdate`, capped at 0.1), so speed does not scale with game speed or pausing; vanilla's `getGameTime():getMultiplier()` style scaling is not applied.

## 6. Can We Make a Single-Player Levitation Mod?

**Yes.** Everything the goal needs, travelling at running speed and levitating up and down, is covered by techniques the mod already uses, and vanilla's own debug fast-move code proves the Z approach works.

### 6.1 What we would reuse

1. **Z hold:** `setZ(z)`, `setLastZ(z)`, `setFallTime(0)`, repeated on every tick while levitating (`holdZ`).
2. **Horizontal push in small steps with wall checks** (`push` and `blocked`), or a simpler version.
3. **Direct key reading in the air**, because the game will not walk an airborne player.
4. **Up and down keys through `PZAPI.ModOptions`.**
5. **Landing detection** (`groundAt` plus `TreatAsSolidFloor`).

### 6.2 What we can drop

- The cloud item, model, clothing XML, and world model. A levitation toggle could instead be a key, a context-menu action, a worn item we already have, or a Ring of the Mage-style item in PseudoMagic.
- The custom animation set. Without it the player will show the vanilla falling pose while in the air, which may look wrong; a standing pose is the main reason this mod has an AnimSet. A first version can accept the vanilla look and add a pose later. (The animation only needs one `.x` clip plus five small XML nodes; the clip would need to be made, which is the only real art task.)
- The sandbox height and speed scaling, the height speed boost, and the loot distribution.
- All multiplayer concerns, if the mod is single-player only.

### 6.3 Matching "running speed"

The Kinto-un default speed of 7 tiles per second, times 1.4 for run, is far above vanilla running; it is a boost, not running speed. To levitate at running speed:

- Measure vanilla's run speed in game (for example, log the player's X and Y every second while running on flat ground and compute tiles per second), then use that as the constant in `push`.
- Or avoid the number altogether: while the player is on the ground, do not push at all (let vanilla move them), and only apply `push` while levitating. At the moment the player leaves the ground the speed would jump unless the constant is matched, so measuring once is still needed.
- `IsoPlayer` has a `runSpeed` variable multiplier (`IsoPlayer.java:437`, exposed as animation variable `RunSpeed`); it is a multiplier, not tiles per second, so measuring displacement is the dependable method.

### 6.4 Suggested minimal design

1. **Toggle:** a key (via `PZAPI.ModOptions`) or an equipped item turns levitation on or off.
2. **Up and down:** hold-to-climb and hold-to-descend keys, as in Kinto-un, with a fixed rate such as 1.2 floors per second, and a configurable maximum height.
3. **Horizontal:** while levitating, read the four movement keys (using the string names, see 5.1), set the forward direction, and push at the measured run speed. Use the same stepped `push`, with free passage over low obstacles if desired.
4. **Landing:** descend until the first solid floor, then stop holding Z and let the game resume. Turning levitation off in the air should glide down, as Kinto-un does, to avoid fall damage.
5. **Safety:** wrap everything in `pcall` as the mod does, and stop levitating when the player enters a vehicle, dies, or is knocked down.

### 6.5 Open questions to settle by testing in game

1. Does the in-air key reading work on v42.20.4 using string key names? (The `KeybindId` calls in this mod probably do not; see 5.1.)
2. What is vanilla's actual running speed in tiles per second?
3. Does the player stay stable at `z` with fractional values between floors (rendering, lighting, and sprite floor level), as Kinto-un's use of fractional height suggests? The mod relies on this, but I did not verify it beyond the code.
4. Does holding Z collide with the engine's `getMinFloorZ()` logic when the player is above an empty square (no floor)? Kinto-un does this, so it probably works.
5. How does the vanilla falling animation look while levitating, and is it acceptable before a custom pose exists?

---

## 7. Recommendation

Build the levitation mod, starting from a stripped-down version of `KintoUn_Client.lua`: `holdZ`, `altitude`, `groundAt`, a simplified `push`, and a corrected key-reading function. Do not copy the key code as is. Test the key reading first, because it is the piece most likely to fail on v42.20.4.

If this becomes a DevCycle in PseudoMagic (for example a levitation item), the first phase should be a one-file prototype that proves up, down, and horizontal movement at a measured run speed. The animation and the item art can follow in later phases.
